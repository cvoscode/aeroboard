# Feature Implementation Plan

Status: implemented across phases 0–6 and the smaller improvements. The original design and acceptance criteria are retained below. See the [workspace guide](../user-guide/workspaces.md) for the shipped behavior and [verification record](workspace-verification.md) for checks, measured costs, and practical limits.

Implementation decisions:

- `catalog.rs` and `workspace.rs` own SQLite metadata and HTTP operations. Legacy and versioned registration share the same name-reservation transaction.
- Objective summaries use an additive `/api/scorecards` contract and an incremental cache integrated with persistence, preserving legacy summary responses. At-step lookup and aggregation retain segment boundaries.
- New Greptime data uses immutable batch-ID-addressed Arrow IPC rows, merged with legacy rows before pagination. This replaces the proposed per-observation identity layout while preserving idempotent visible effects.
- The SDK outbox commits IPC payloads and control records together in SQLite rather than separate manifest/files. Ordered transactions, checksums, and an OS owner lock define the local durability boundary.
- First-use registration in memory-only mode remains synchronous; explicit context entry or resolving `run.run_id` performs setup before training. Disk-outbox registration is deferred without network waits.

## Scope and delivery order

Implement the seven proposed features and the four smaller improvements while keeping Aeroboard focused on local training workflows. Ship independently useful increments, starting with run lifecycle and goal-aware metrics.

| Phase | Deliverable | Dependencies | Release |
| --- | --- | --- | --- |
| 0 | Persistent run/project metadata, stable identities, capability negotiation | Existing storage and ingestion | Foundation |
| 1 | Run lifecycle, heartbeats, explicit resume | Phase 0 | First release |
| 2 | Metric definitions, useful scorecards, best/last/at-step comparison | Phases 0–1 | First release |
| 3 | Run organization, provenance, search, and saved project views | Phases 0–2 | Second release |
| 4 | Baseline and multi-seed comparisons | Phases 2–3 | Third release |
| 5 | Events connected to charts and media | Phases 0–2; project selection from phase 3 | Third release |
| 6 | Durable offline capture, recovery, and replay | Phase 1; server idempotency work in phase 6A | Fourth release |
| Small improvements | Metric search, logarithmic axes, chart/CSV export, individual archive/delete | Scheduled alongside the relevant phases below | Incremental |

Phase numbers describe integration order. In particular, offline capture cannot ship before retry-safe server writes. Project identity is introduced before project views even though the richer project management UI arrives later.

## Current implementation to extend

The existing implementation already provides:

- Scalar, hyperparameter, image, audio, and video logging over Arrow Flight.
- A background sender with retries, a bounded memory queue, and dropped-row accounting in `aeroboard-client/src/aeroboard_client/_sender.py`.
- Server acknowledgement after persistence through `ingestion.rs`, `t_junction.rs`, and `persistence.rs`.
- Filesystem JSONL storage, optional GreptimeDB storage, and live-only mode through `StorageEngine`.
- Incremental last/min/max summaries in `aeroboard-server/src/summaries.rs`.
- WebSocket reconnection and history catch-up in `aeroboard-web/src/hooks/useAeroboard.ts`.
- Chart defaults and browser overrides through `dashboardDefaults.ts` and `useDashboardPreferences.ts`.
- Run comparison tables and parallel coordinates. The table currently selects the last metric value.

Reuse these paths. Extend the summary cache and background sender instead of creating independent ingestion or chart pipelines.

## Shared architectural decisions

### Separate mutable metadata from telemetry

Introduce a `CatalogStore` for projects, run metadata, sessions, metric definitions, saved views, annotations, and ingestion receipts. Use an embedded SQLite catalog at `<data_dir>/catalog.sqlite` for persistent deployments and an in-memory implementation for live-only mode. Execute database/file work away from Tokio's async workers.

Keep bulk scalar/media data behind the existing `StorageEngine`. Both filesystem and Greptime deployments use the catalog, so Greptime deployments must also retain and back up the server data directory. This plan targets one server owning a catalog; multiple server writers require separate coordination work.

Version catalog migrations and API payloads. Import existing run manifests or backend run listings into a default project without rewriting their telemetry. Retain legacy readers for existing JSONL, JSON, and Arrow layouts.

### Establish stable identities

Add an immutable `run_uid` generated by the SDK before network contact. Preserve the existing canonical `run_id` and its auto-versioning behavior for stored rows and legacy APIs; keep a mapping in the catalog. A user-editable display name must not rename stored telemetry.

Add `project_id`, `session_id`, monotonically ordered session attempts, and request IDs for idempotent control operations. Resuming creates a new session for the same run. Conflicting active writers return a conflict instead of silently sharing a run.

Reserve stable batch IDs and sequence numbers in the protocol now. Implement durable telemetry deduplication in phase 6A before relying on those identifiers for offline replay.

### Keep control operations explicit

Use HTTP for catalog operations and Arrow Flight for bulk telemetry. SDK control calls use bounded timeouts and a background delivery queue during training; heartbeat traffic must not wait behind large media uploads. Begin run/session setup before entering the training loop. Explicit offline mode can defer registration using the client-generated identities.

Add `GET /api/capabilities` with protocol version, supported features, persistent server-store identity, storage mode, and delivery acknowledgement semantics. Existing clients and existing `/api/config` responses remain supported. New clients must report unsupported requested features clearly; offline replay and explicit resume cannot silently fall back to weaker semantics.

Broadcast catalog updates through a typed control message on `/ws/live`. Extend the existing text-message handling alongside binary Arrow messages. Include revisions and refresh metadata after a reconnect or sequence gap. Preserve current best-effort live streaming and history catch-up behavior.

New `PATCH` routes require updating the explicit CORS method allow-list in `main.rs`. Add consistent validation errors, conflict responses, pagination, and request-size limits to the new routes.

## Phase 0: Metadata and compatibility foundation

Implementation:

1. Add `catalog.rs`, versioned catalog migrations, and shared metadata types. Wire the catalog into `AppState` and configuration.
2. Create project and run records, immutable identity mappings, session records, and a default project for existing runs. Mark imported lifecycle data as unknown; do not infer that historical runs completed successfully.
3. Add capability discovery, idempotent run registration, revisions for mutable records, and typed metadata updates on the live socket.
4. Keep `GET /api/runs` and existing history response shapes compatible. Introduce a separate paginated `GET /api/run-records` for richer run listings.
5. Define a versioned Flight envelope containing run/session identity, batch ID, sequence number, and payload checksum. Accept older uploads without the envelope; advertise their weaker replay guarantees.

Acceptance criteria:

- Existing scripts, dashboards, and stored runs continue to work without a data reset.
- Retrying registration with the same request/run UID returns the same run; concurrent new runs still get distinct canonical names.
- Migration interrupted at any step can restart safely. Missing catalog metadata can be imported without inventing run outcomes.
- Live-only metadata disappears on server restart and remains clearly identified as ephemeral.
- Filesystem and Greptime users can back up and restore the catalog together with their telemetry backend.

## Phase 1: Run lifecycle and resume

### Behavior

Track execution status separately from telemetry delivery status. Execution states are `running`, `completed`, `failed`, and `cancelled`; imported runs can be `unknown`. Show `stale` as a derived indication that a running session stopped sending heartbeats, rather than declaring it failed.

Start with a 15-second heartbeat interval and a configurable 60-second stale threshold. Use server receipt time for heartbeat freshness. Late telemetry or replayed historical heartbeats must not make an old process appear alive.

Expose start/end time, last heartbeat, last metric time, duration, session attempt, and available failure details. A resumed run retains its history and acquires a new session lease. Fence old session control updates so they cannot overwrite the resumed run's state.

### SDK, server, and dashboard work

- Add `finish(status=...)`, context-manager support, heartbeat management, and explicit resume to `AeroboardClient` and the module-level API. A normal context exit completes the run; an exception fails it; keyboard cancellation marks it cancelled. Keep `close()` focused on transport cleanup for backward compatibility.
- Map Lightning finalization and Ray trial completion/failure to lifecycle events. Respect the existing rank-zero logging behavior for distributed training integrations.
- Add run/session registration, heartbeat, finish, and resume operations to the catalog API. Finish records carry the final telemetry sequence so the UI can show execution complete while data is still synchronizing.
- Show per-run status badges in the sidebar and comparison table. Keep browser/server connection status separately visible. Provide an explicit resume identifier in run details.
- Record resumed session boundaries. Continue global training steps by default; a user who restarts step numbering must declare a new segment so comparisons do not silently combine overlapping steps.

Proposed usage:

```python
client = aeroboard.init(run_id="baseline", project="classifier")
client.log_metrics({"val/loss": 0.12}, step=100)
client.finish(status="completed")

# In a later training process, use the exact identifier returned for that run.
client = aeroboard.init(run_id=existing_run_uid, resume=True)
```

Acceptance criteria:

- Normal completion, exception, cancellation, process termination, server restart, and explicit resume produce distinct and explainable states.
- Killing a process results in stale status after the threshold, never an invented successful finish or confirmed failure.
- A quiet training loop remains running while heartbeats arrive. A connected browser alone cannot keep a training session alive.
- Delayed finish/heartbeat messages from an earlier session cannot change the current session's state.
- Training continues through heartbeat delivery failures, and pending telemetry is represented separately from execution outcome.

## Phase 2: Metric definitions and goal-aware summaries

### Definitions and scope

Add a `MetricDefinition` containing full metric name, optional goal (`minimize` or `maximize`), unit, optional target, and revision. Store project defaults with run-specific overrides. Display targets from saved views/browser edits remain presentation overrides and must not silently change the objective used to rank experiments.

Evaluate objectives per full metric name. Grouped scalar charts may contain both `train/loss` and `val/loss`; their summaries and goals stay distinct. Preserve existing chart-name matching for legacy dashboard target configuration.

Add `client.define_metric(...)` and expose definition editing in run/project settings. Unknown goals must remain unspecified; do not guess from metric names.

```python
client.define_metric("val/accuracy", goal="maximize", target=0.95, unit="fraction")
client.define_metric("val/loss", goal="minimize", target=0.1)
```

### Summary and comparison behavior

Extend `MetricStats`, `RunSummary`, and the frontend types with best value, best step/time, last step/time, finite-sample count, and first target crossing. Preserve the existing last/min/max fields.

Use finite values for best scores and target crossings. Keep NaN/Infinity visible as diagnostic observations; do not rank them as winners. Break equal best scores by the earliest recorded crossing, with a stable point-order tie-break. Recompute affected derived summaries when an objective changes, and key caches by the definition revision.

Define time to target as elapsed captured wall time from the first recorded metric sample to the first qualifying sample; resumed gaps are included. Keep this distinct from an estimate of active compute time.

Add comparison selectors for `best`, `last`, and `at step`. At-step lookup uses the last valid observation at or before the requested step, only within that run segment's observed step range. Show missing values outside that range; never extend a finished run indefinitely to match a longer one. Historical data without steps supports time alignment and displays missing step-based summaries.

Show goal-aware scorecards and target progress. A final score is the last observation of a completed run; failed/running runs remain available with explicit status rather than receiving a final score.

Acceptance criteria:

- Minimize, maximize, zero/negative targets, equal best scores, non-finite values, missing metrics, and out-of-order arrival have deterministic results.
- Live summaries agree with a cold rebuild from persisted history for both storage backends.
- Changing a goal or target refreshes its dependent scorecards without rewriting raw data.
- At-step comparisons identify missing coverage and resumed segments explicitly.

Small improvements in this phase: metric-name search and per-chart linear/logarithmic y-axis controls. Logarithmic mode must make excluded nonpositive samples visible to the user and preserve target-line behavior.

## Phase 3: Organization, provenance, and saved views

### Run organization and provenance

Extend run metadata with project membership, display name, tags, notes, archive state, and captured provenance: Git commit/dirty state, seed, dataset identifier/version, framework version, and optional user-provided fields.

Capture inexpensive local provenance once at run start. Allow automatic capture to be disabled or overridden. Preserve original captured metadata separately from editable labels and notes.

Add a paginated run browser with filters for project, status, tags, parameter values, and objective-aware metric thresholds. Use structured filter objects and a fixed operator allow-list; compile filters on the server instead of evaluating user expressions. Preserve the current text search as the simple entry point.

Archive and unarchive individual or selected runs through metadata updates. Archived runs remain queryable when explicitly included and can still receive telemetry.

### Saved project views

Add versioned, named project views containing starred/hidden charts, order, widths, axes, smoothing, display targets, run filters, selected runs, baseline, and comparison reducer. Support save, save as, rename, delete, and setting the project's default view.

Resolve presentation settings in this order, with field-specific inheritance:

1. Browser overrides for the active project/view.
2. The explicitly selected view, or the project's default view when none is selected.
3. Per-run dashboard configuration.
4. Server TOML defaults.

Keep the distinction between an unset target and an explicit removed target (`null`). Reset layout clears browser overrides and reapplies the selected/default view plus inherited settings. Resetting does not delete a saved view.

Scope browser preferences by server-store identity, project, and view. Offer a one-time import of existing global browser preferences into the default project; do not apply them to every project. Theme remains a browser-wide preference.

Share links using stable project/view/run identifiers. Links resolve only on a reachable deployment with access to those records. Handle deleted views or missing runs with a clear fallback. Use revision checks for saves; a conflicting edit returns a conflict and lets the user reload or save a copy.

Acceptance criteria:

- A view saved in one browser opens with the same settings in a fresh browser.
- Browser changes in one project/view do not affect another, and legacy preferences can be imported without losing explicit target removals.
- A stale save cannot silently overwrite a newer view revision.
- Structured filtering, pagination, archive/unarchive, and metadata round-trips work consistently across backends and restarts.
- Old runs without provenance remain usable and display missing metadata honestly.

## Phase 4: Baseline and multi-seed comparison

Add a pinned baseline to comparison views. Show absolute deltas and relative improvement using the selected metric goal/reducer. For minimize goals, an improvement is baseline minus candidate; reverse that for maximize goals. Do not calculate a percentage against a zero baseline or rank incompatible metric units/definitions.

Add a configuration diff highlighting changed hyperparameters and provenance. Default multi-seed grouping uses an explicit experiment/configuration group, excluding seed and lifecycle fields. Keep dataset version and metric definition compatible within a group, and let users choose grouping fields deliberately.

Start with mean curves and sample standard deviation bands. Show the contributor count at each step and hide the variability band for fewer than two observations. Label the band as standard deviation, without implying a confidence interval.

Use exact step matching for the first release. Missing observations remain missing, and curves are not extrapolated beyond a run's extent. Add interpolation later only as an explicit, bounded option. Runs without steps can be compared in a separately selected time-alignment mode.

Implement a bounded, cached server aggregation endpoint so the browser does not need to fetch every raw curve. Deduplicate repeated observations within each run before grouping; one run supplies at most one observation per aligned position. Aggregate raw values before downsampling for display, and leave source data unchanged.

Acceptance criteria:

- Hand-calculated fixtures agree with mean, standard deviation, baseline deltas, and contributor counts.
- Missing steps, unequal run lengths, repeated samples, mixed units, one-seed groups, and resumed segments cannot produce misleading complete coverage.
- Aggregation cache keys include run data revisions, metric definition revisions, grouping, reducer, and alignment.
- Failed/running runs can be explicitly included; the default finished-run comparison makes the selected population visible.

## Phase 5: Events linked to charts and media

Add an event model with stable event ID, run/session identity, captured timestamp, optional step/segment, kind, label, optional structured details, and referenced media/checkpoint IDs.

Provide `client.log_event(...)` for SDK events and annotation CRUD for dashboard notes. Start with manual notes, checkpoint references, learning-rate changes, and user-reported warnings. Checkpoints are references and metadata; this phase does not require uploading model weights.

Add optional step/segment and stable asset IDs to media metadata. Preserve legacy timestamp/name content lookups and media without steps. Events and media may arrive in either order; resolve links as their referenced data becomes available.

Show event markers on scalar charts and an event list for the selected run. Selecting a marker reveals its details and associated media at that recorded position. A media selection can highlight the corresponding chart position. Keep heavy clip bytes on the existing lazy-loading path.

Acceptance criteria:

- Notes survive reloads and SDK retries do not duplicate an event ID.
- Two clips logged within the same millisecond retain separate identities and correct event associations.
- A late media upload resolves an existing event link without moving the event to a different step.
- Old timestamp-only media, missing attachments, and empty event lists remain usable.

## Phase 6: Durable offline capture

### 6A: Retry-safe ingestion is the prerequisite

Implement the versioned batch envelope introduced in phase 0. A replay retains its run UID, session ID, sequence number, batch ID, checksum, and captured timestamps. New-protocol uploads contain one identified batch per RPC. Reusing a batch ID with different contents is a permanent validation error.

A receipt check alone is insufficient: the server can crash after writing telemetry but before recording the receipt. Make visible storage effects idempotent across that window:

- For filesystem storage, write new-protocol batches as immutable batch-ID-addressed segments, commit them atomically, and treat query indexes as rebuildable projections. Continue reading legacy JSONL/Arrow data.
- For Greptime, persist stable batch/row identities in versioned rows and deduplicate retries before pagination, summaries, and aggregation. Prove this path against the supported Greptime version; physical duplicate rows may exist, but must not count twice in Aeroboard results.
- Commit the receipt only after the backend's durable operation succeeds. A retry after receipt loss must recover the existing logical batch. Suppress duplicate live publication, or let clients discard duplicate batch IDs, including the crash-recovery case.
- Retain run-deletion tombstones and storage generations so a delayed outbox cannot recreate deleted data.

State the guarantee as at-least-once delivery with idempotent visible effects. Live-only mode can acknowledge receipt but cannot claim persistent server storage; expose that distinction through capabilities and delivery status.

### 6B: Disk-backed SDK outbox and recovery

Extend `_sender.py` with a pluggable persistent outbox. Write normalized Arrow IPC batches plus a versioned manifest, media bytes, sequence information, and checksums. Use a single owner per outbox and atomic file replacement for state changes.

Persist pending control operations as well: run/session registration, metric definitions, SDK events, and finish records. Replay their dependencies before the telemetry that references them, and retain the final telemetry watermark on finish. Historical heartbeat records can be retained as diagnostics but are never replayed as fresh heartbeats.

Keep logging calls independent of network waits. A background writer moves data from the bounded memory queue to disk. Define the durability boundary: ordinary logging can have a small uncommitted memory window; `flush(local_only=True)` waits for local fsync, while normal `flush()` also attempts server delivery. `close()` preserves locally committed, unacknowledged batches after its delivery timeout.

Bind each outbox to the persistent server-store identity, project/run UID, and session. Never silently replay it into a different server store or create a new run version on every retry. Registration requests remain idempotent when the canonical run name is assigned after an offline start.

For a first offline start against a server the client has never contacted, record the configured endpoint with an unbound store identity. The first successful capability handshake establishes that binding. Subsequent synchronization must match the established server-store identity, including after client restarts.

Add configurable disk quotas and visible queue/error counters. Start with a configurable 1 GiB outbox limit. On exhaustion, stop accepting additional durable data, report the loss/failure counters, and let training continue; do not silently remove committed unacknowledged data. Make alternative eviction behavior explicit if added later.

Provide `aeroboard sync --spool-dir PATH` to inspect and drain a stopped process's outbox. Remove files only after a matching acknowledgement. Quarantine corrupt entries with diagnostics instead of retrying forever. Replayed historical control records cannot refresh heartbeat freshness or regress the current run state.

Acceptance criteria:

- Capture with the server unavailable, terminate the client after a local flush, restart, and recover every locally committed batch.
- Crash the server before write, after write/before receipt, and after receipt/before acknowledgement; each logical observation and event appears once after replay.
- Repeat the scenarios for filesystem and real Greptime storage, including media, summaries, live views, and aggregation.
- Full disk, quota exhaustion, corrupt entries, competing outbox owners, wrong server identity, and permanent rejection produce bounded, inspectable outcomes.
- Replay into archived runs works; replay into deleted generations is rejected without resurrection.

## Verification and release gates

Use meaningful state, storage, and integration tests rather than tests that merely repeat field assignments. Extend the existing Python tests, Rust integration suite, and frontend Node tests. Add browser-level scenarios for saved views, lifecycle, comparison interactions, and media/event selection.

Run the checks relevant to each change, and run the complete CI suite at release boundaries:

```bash
uv run pytest
```

```bash
cd aeroboard-server
cargo clippy --all-targets -- -D warnings
cargo test
```

```bash
cd aeroboard-web
npm run lint
npm test
npm run build
```

```bash
python -m sphinx -b dirhtml -W --keep-going docs docs/_build/dirhtml
```

Measure SDK logging latency, memory/outbox growth, server ingestion throughput, summary latency, aggregation latency, and dashboard responsiveness against the existing implementation using the same fixture workloads. Record results with the PRs that change those paths. Keep live history/media retrieval bounded and ensure metadata/heartbeat work does not starve telemetry persistence.

Release gates:

- First release: phases 0–2 work end to end; old clients and old stored runs remain readable.
- Second release: projects and saved views survive restarts and work in a fresh browser; archive and exports are usable.
- Third release: baselines, multi-seed statistics, and linked events/media handle partial and unequal data honestly.
- Fourth release: fault-injection tests prove durable replay and idempotent visible effects for both persistent storage backends. Do not enable durable delivery guarantees based solely on a successful normal upload.

Calendar estimates should be assigned after PRs 01–02 establish the migration and protocol costs. PRs 14–15 are the largest reliability risk and should be reviewed as storage/protocol changes, not treated as a small queue enhancement.
